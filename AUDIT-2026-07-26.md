# Ascend Roofing Group — Full Site Audit (2026-07-26)

The site is structurally sound — 207/207 tests pass, the build is deterministic, SQL is fully parameterised, and there is no injection or secret leakage in the page source — but it has three defects that are actively costing you money and legal exposure right now. Since the 2026-07-10 audit, PRs #21 and #22 genuinely fixed a lot (skip-link markup, AVIF images, cache headers, rate-limit helper, cron auth, Places API migration, colour-swatch keyboard access, footer contrast, button contrast), but several of those fixes were applied to some pages and not others, and two of them regressed something else: the git-derived sitemap date now breaks CI on every run, and the skip link that was added does not actually move keyboard focus.

The single most urgent thing: **anyone on the internet who knows a subcontractor's or employee's email address can silently overwrite their stored bank account details** via `/api/submit-subby-pack` or `/api/submit-new-employee` (C-1). That is a payment-redirection fraud path with no authentication in front of it, and the confirmation email masks the account number so the change looks routine. Fix that before anything else.

Close behind it: the contact form on five of your service pages (roof repairs, gutters, new installs, insulation, skylights) throws a JavaScript error on submit and **silently discards 100% of enquiries** — no error message, no email, nothing (C-2). And your homepage still promises a workmanship warranty "for life" while your published Terms cap it at 10 years (H-17).

## Critical

### C-1 · `unauthenticated-bank-detail-overwrite` — Anyone who knows a subcontractor's or employee's email can overwrite their stored bank details

**Files:** `api/submit-subby-pack.js:108-119`, `api/submit-subby-pack.js:134-137`, `api/submit-new-employee.js:136-162`, `lib/verify-origin.js:29-38`

**What's wrong**

```sql
ON CONFLICT (email)
DO UPDATE SET
    ...
    bsb = EXCLUDED.bsb,
    account_number = EXCLUDED.account_number,
    account_name = EXCLUDED.account_name,
```

```js
await sql`
    DELETE FROM insurance_documents
    WHERE subcontractor_id = ${subcontractorId} AND document_type = ${type}
`;
```

The only gate is `api/submit-subby-pack.js:16` `if (!verifyOrigin(req))`, and `lib/verify-origin.js:31-37` reads only `req.headers.origin` / `req.headers.referer` — headers any `curl` can set. `api/submit-new-employee.js:136-161` has the identical `ON CONFLICT (email) DO UPDATE SET ... bsb = EXCLUDED.bsb, account_number = EXCLUDED.account_number`.

**Impact.** These are unauthenticated public endpoints. A subcontractor's business email is usually published on their own website. One scripted POST with that email plus attacker-controlled BSB and account number replaces the real payment details on the existing `subcontractors` row — textbook payment-redirection fraud. The confirmation email to you shows only masked digits (`maskTail`, `submit-subby-pack.js:277-281`), so the change looks like a routine resubmission. The same request replaces the victim's public-liability and workers-comp rows with attacker-supplied data, corrupting the compliance record the expiry cron depends on. The 3-per-hour rate limit is irrelevant — one request is enough. The attacker must also supply two files that pass `lib/sanitize.js` `validateUpload`, which raises effort trivially, not meaningfully.

**Fix.** Do not let an unauthenticated POST mutate an existing row. Either (a) issue signed, single-use invitation tokens for both HR forms and require the token to match the email, or (b) make the insert append-only (`INSERT … ON CONFLICT DO NOTHING`, or a separate `submissions` table) and require a human to promote a submission to the live record. Never `DELETE` existing `insurance_documents` from an unauthenticated path — insert a new version and let staff retire the old one.

*Newly discovered — not in the 2026-07-10 audit.*

### C-2 · `contactform-submitbtn-null-5-service-pages` — Contact form on 5 service landing pages throws on submit; every enquiry is silently discarded

**Files:** `script.js:188`, `script.js:189`, `script.js:191`, `script.js:193`, `gutters-downpipes-brisbane.html:248`, `gutters-downpipes-brisbane.html:267`, `new-roof-installation-brisbane.html:274`, `new-roof-installation-brisbane.html:294`, `roof-insulation-brisbane.html:233`, `roof-insulation-brisbane.html:253`, `roof-repairs-brisbane.html:281`, `roof-repairs-brisbane.html:303`, `skylights-whirlybirds-brisbane.html:252`, `skylights-whirlybirds-brisbane.html:273`

**What's wrong**

```js
contactForm.addEventListener("submit", async (e) => {
    e.preventDefault();

    const btn = document.getElementById("submitBtn");
    const errorEl = document.getElementById("contactError");
    const originalHTML = btn.innerHTML;
```

The submit button on these five pages carries no id:

```html
<button type="submit" class="btn btn-primary btn-lg btn-full">
```

All five have `id="contactForm"` (e.g. `gutters-downpipes-brisbane.html:248`), but `grep -c 'id="submitBtn"'` returns 0 on all five. `index.html:910`, `roof-replacement.html:579`, `template.html:582` and the root Colorbond blog page all have it correctly. None of the five pages has a competing inline handler — the only script is `<script defer src="script.js">`.

**Impact.** `document.getElementById("submitBtn")` returns `null`, so `btn.innerHTML` throws a TypeError. The handler is `async`, so the throw becomes an unhandled promise rejection: nothing is logged visibly, no message shows, the button never changes, and nothing is sent to `/api/submit-quote`. `e.preventDefault()` has already run at line 189, so the form's own `action="/api/submit-quote" method="POST"` native fallback is suppressed too. **Fix.** Add `id="submitBtn"` to the `<button type="submit">` on all five pages. Then harden `script.js` so a missing element can never eat a lead: replace `document.getElementById("submitBtn")` with `contactForm.querySelector('button[type="submit"]')` so it never depends on an id, and if it is still null, `return` **before** `e.preventDefault()` so the native POST fires. Add a CI assertion that every page containing `#contactForm` also contains `#submitBtn` and `#contactError`.

### C-3 · `file-upload-keyboard-blocker` + `file-input-display-none-keyboard-inaccessible` — Required file uploads are impossible to use with a keyboard

**Files:** `new-employee-form.html:223`, `new-employee-form.html:624`, `new-employee-form.html:626`, `new-employee-form.html:635`, `new-employee-form.html:854`, `subcontractor-pack.html:202`, `subcontractor-pack.html:474`, `subcontractor-pack.html:475`, `subcontractor-pack.html:690`

**What's wrong**

```css
.file-upload-input {
    display: none;
}
```

```html
<label for="publicLiability" class="file-upload-label"> ... Choose File </label>
<input type="file" id="publicLiability" name="publicLiability"
    class="file-upload-input" accept=".pdf,.jpg,.jpeg,.png" aria-required="true">
```

The code even documents the consequence at `subcontractor-pack.html:689-691`:

```js
// JS-level validation for required file inputs (HTML5 `required`
// can't be used because the inputs are display:none — browsers
// refuse to focus hidden invalid fields and silently block submit).
```

All six file inputs across the two forms carry `class="file-upload-input"`, so all six are `display:none`. There is no `tabindex` on the label, no `click()` proxy, no keydown handler.

**Impact.** `display: none` removes the input from the tab order **and** from the accessibility tree. A `<label>` is not focusable and does not respond to Enter or Space, so there is no keyboard path to open the file picker at all. Public Liability + Workers Comp (`subcontractor-pack.html:692-706`) and Photo ID + White Card (`new-employee-form.html:854-868`) are hard-required by the JS validator and by the server (`api/submit-subby-pack.js:36`, `api/submit-new-employee.js:57`). A keyboard-only or screen-reader subcontractor or employee can fill every text field, reach Submit, be told "Public Liability Insurance is required", and have no reachable control to satisfy it. `aria-required="true"` on line 475 is inert because the element is not exposed. Two labels also point at the same id (`new-employee-form.html:624` and `:626`), so the accessible name would be a concatenated mess even if it were exposed. WCAG 2.1.1 Keyboard, Level A — a hard hiring and subcontractor-onboarding blocker.

**Fix.** Never `display:none` a file input. Use the visually-hidden pattern: `.file-upload-input { position:absolute; width:1px; height:1px; clip-path:inset(50%); overflow:hidden; }` so the input keeps focus and its accessible name. Add `.file-upload-input:focus-visible + .file-upload-label { outline: 3px solid var(--accent-color); outline-offset: 2px; }` so the styled label shows the focus ring. Remove the duplicate `<label for="photoId">` (keep the descriptive one; make the button text a `<span aria-hidden="true">` inside the styled label). With the input focusable you can also drop the JS-only validation workaround and restore native `required`.

**Files:** `api/cron/check-expiring-insurance.js:42`, `:59-63`, `:129-141`, `:225-231`

**What's wrong**


**Impact.** The comment at line 42 promises 30/60/90-day reminders.
